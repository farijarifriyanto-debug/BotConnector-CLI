## PACKAGING_IDENTITY (candidates for change, only if truly needed)

- **`packages/opencode/package.json`** — `"name": "opencode"`, `"bin": { "opencode": "./bin/opencode" }`. This
  is the actual binary published and what `npm i -g opencode-ai` installs (per `packages/opencode/script/build.ts`,
  built binaries are named `opencode-<os>-<arch>[-baseline][-musl]`, embedding `pkg.name` into the compiled
  artifact filename, the `--user-agent` string sent to model providers
  (`--user-agent=opencode/${Script.version}`), and burned-in `OPENCODE_VERSION`/`OPENCODE_CHANNEL` defines).
  Renaming this is the highest-leverage, highest-risk change — touches the compiled binary name, the shipped
  npm package, the user-agent string providers see, and every doc/install instruction. Only in scope if
  BotConnector will actually publish its own binary under a new name.
- **`packages/cli/package.json`** — `"name": "@opencode-ai/cli"`, but `"bin": { "lildax": "./bin/lildax.cjs" }`.
  This is a **separate, second CLI** with its own bin name "lildax" (not "opencode"), depending on
  `@opencode-ai/core`, `@opencode-ai/server`, `@opencode-ai/tui`, with commands like `service start/stop/status`,
  `serve`, `daemon`, `api`, `migrate` — looks like a lighter daemon/service-mode entry point, distinct from the
  full interactive `packages/opencode` binary. **"lildax" does not appear anywhere else in the branding
  surface** — it doesn't match any known internal codename convention we found elsewhere in the repo. This is
  the most important open question in this report: is `packages/cli` even part of what ships as BotConnector,
  and if so, does "lildax" get touched at all (it's arguably its own product identity, one level below
  opencode branding)? See open questions.
- `packages/desktop/electron-builder.config.ts` — `appId: "ai.opencode.desktop[.dev|.beta]"`,
  `productName: "OpenCode"/"OpenCode Dev"/"OpenCode Beta"`, GitHub publish targets

## Repo structure notes

No official "custom distribution" guide exists in this repo (confirmed). Map of relevant packages:

- **`packages/opencode/`** — the real, shipped CLI/TUI binary. `package.json` name `"opencode"`, bin
  `opencode`. Owns `script/build.ts` (compiles per-platform binaries, embeds an entire pre-built copy of
  `packages/app`'s web UI into the binary for the local web-view mode), the ASCII splash banner
  (`src/cli/cmd/run/splash.ts`), yargs CLI scaffold (`src/index.ts`), and essentially all agent/tool/session
  runtime logic (out of scope — behavioral).
- **`packages/cli/`** — a second, smaller CLI (`bin: lildax`), daemon/service-oriented (`service
  start/stop/status/restart`, `serve`, `daemon`, `api`, `migrate`). Depends on `@opencode-ai/core`,
  `@opencode-ai/server`, `@opencode-ai/tui` — looks like a thinner entry point for headless/service use, wired
  through `@opencode-ai/cli-<platform>-<arch>` published binaries (same shim pattern as `packages/opencode/bin/opencode`).
  Its relationship to `packages/opencode` isn't self-documented; needs a human call (see open questions).
- **`packages/tui/`** — the actual terminal UI: SolidJS + `@opentui/*`-based components (dialogs, sidebar,
  home screen, prompt, themes). Owns the ASCII wordmark logo, terminal title, home-screen tips, sidebar
  footer copy, and the theme system (including the `opencode` built-in theme name).
- **`packages/desktop/`** — Electron desktop app (BETA). Main process (`src/main/`), preload, and a SolidJS
  renderer (`src/renderer/`) with ~70 locale files. Uses `@opencode-ai/app` and `@opencode-ai/ui` as its UI
  layer. Ships per-channel (dev/beta/prod) via `electron-builder`.
- **`packages/server/`** — the HTTP/API layer (`src/handlers/*.ts`, `src/routes.ts`, `src/api.ts` via
  `@opencode-ai/protocol`). Sampled handlers show no hardcoded product-name strings in routes/responses —
  branding-neutral by design. Relevant to the product owner's stated "cloud/server use" plan for this variant;
  low branding surface but worth a targeted re-check once the API is actually stood up under the BotConnector
  name (things like OpenAPI `title`/`description` fields, if any, weren't found in the sampled files but the
  full `@opencode-ai/protocol/api` schema wasn't exhaustively read).
- **`packages/app/`** — **not** primarily a "desktop counterpart" in the sense implied by the task brief; it's
  the shared web UI (`@opencode-ai/app`, SolidJS) that is both (a) embedded into the compiled `opencode`
  binary as the local web view (built by `packages/opencode/script/build.ts`), and (b) used as the renderer
  inside `packages/desktop`. One codebase, two delivery surfaces. `dev:web` at the root maps here.
- **`packages/web/`** — the live opencode.ai marketing + docs site (Astro + Starlight theme, deployed via
  Cloudflare adapter). Confirmed via `config.mjs` (`url: "https://opencode.ai"`) and README links. This is the
  parallel concern to the goose marketing-site work already done in this session.
- **`packages/docs/`** — a **separate** Mintlify-based docs config (`docs.json`, `.mdx` files, own `LICENSE`).
  Its navbar/footer still point at Mintlify's own accounts/support address, suggesting it may be unfinished
  scaffolding rather than something actually deployed. Needs confirmation before assuming it's in scope.
- **`packages/console/`** (`app/`, `core/`, `function/`, `mail/`, `resource/`, `support/`) — **not mentioned in
  the task brief, but directly relevant.** This is a cloud console/dashboard product: `@opencode-ai/console-app`
  has Stripe billing keys, `auth.dev.opencode.ai` references, and it is where the root `README.md`'s own logo
  SVGs live (`packages/console/app/src/asset/logo-ornate-{dark,light}.svg`). Given the product owner's stated
  intent ("this opencode-based BotConnector variant is intended for CLI/TUI and cloud/server use"), this
  console/dashboard package is plausibly **more** relevant to the eventual rebrand than the desktop app is —
  flagging prominently for a scoping decision.

## Open questions / judgment calls for the product owner

1. **`packages/console/` was not in the original scoping list but looks highly relevant.** It's a cloud
   billing/auth dashboard (`@opencode-ai/console-app`, Stripe, `auth.dev.opencode.ai`) and is the actual source
   of the logo assets the root README displays. Given the stated cloud/server focus for this variant, should
   this package be added to the branding inventory/rebrand scope in a follow-up pass?
2. **`packages/cli` ("lildax") — what is it, and is it in scope at all?** It's a second CLI entry point with
   its own bin name "lildax" (not "opencode"), targeting service/daemon-style usage (`service start/stop`,
   `serve`, `daemon`). It isn't referenced from the README's installation instructions and its relationship to
   `packages/opencode` (the "real" CLI) isn't documented anywhere we found. Needs a human decision: is this
   shipped at all in the BotConnector variant, and if so, does "lildax" get renamed too, left alone as its own
   sub-brand, or is the whole package dropped?
3. **Desktop app scope (explicitly asked to flag):** goose remains the desktop surface per the product owner;
   this opencode fork targets CLI/TUI + cloud/server. `packages/desktop/` has a full branding surface (window
   title, macOS/Windows app name, ~70 locale files with app-name strings, icon sets, installer naming, custom
   URL protocol `opencode://`) that would need real design/asset work (new `.icns`/`.ico`/Windows-Store tile
   set) if rebranded. Recommend: **skip `packages/desktop` entirely in the eventual rebrand pass** unless the
   product owner has a concrete reason to ship a BotConnector desktop build alongside goose's. This report
   inventories it fully so the option is documented, not because it's recommended.
4. **The literal CLI command name (`opencode` as something users type).** A large share of the "BRANDING_VISIBLE"
   text found (home-screen tips, splash exit-hint `opencode --mini -s <id>`, install script, README command
   examples, `.scriptName("opencode")` in yargs) is really the *command name*, not just marketing copy. Copy-
   editing "OpenCode" → "BotConnector" in prose without renaming the actual binary/command produces an
   inconsistent product (docs say "BotConnector" but you still type `opencode run`). Recommend deciding, before
   any edit pass: does BotConnector ship its own renamed binary (`botconnector`/similar, a real
   PACKAGING_IDENTITY change touching `packages/opencode/package.json`, `bin/opencode`, `script/build.ts`,
   install script, README command examples, and the yargs `scriptName`), or does it keep the `opencode` command
   name and rebrand only the surrounding prose/logo/window titles? This is the single highest-impact scoping
   decision for the whole effort.
5. **`packages/docs/` (Mintlify) vs `packages/web/` (Astro/Starlight) — which one is actually live?**
   `packages/docs/docs.json` still has Mintlify's own unconfigured support email/socials, suggesting it may be
   dead/unfinished scaffolding, while `packages/web/` is confirmed live at opencode.ai via `config.mjs`. Worth
   confirming with the product owner (or checking deploy/CI config) before spending effort rebranding
   `packages/docs/` content that may not ship.
6. **The built-in `"opencode"` color theme** (`packages/tui/src/theme/assets/opencode.json`, selectable by name
   in the theme picker). Low-stakes but user-visible. Recommend leaving as-is (it's a theme name, not a claim
   of product identity) unless the product owner specifically wants it renamed/removed/replaced with a
   BotConnector-branded theme.
7. **`packages/web/package.json` depends on `"opencode": "workspace:*"` as a devDependency.** Should be
   understood (likely used to generate CLI reference docs from `--help` output at build time) before any binary
   rename, since it's a real build-time coupling between the docs site and the CLI package name/bin.

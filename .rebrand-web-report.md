## What packages/web actually is

Confirmed by reading `astro.config.mjs`, `config.mjs`, `package.json`, and sampling
`src/content/docs/*`: `packages/web` is the **Starlight-based documentation site**
(Astro 5 + `@astrojs/starlight` + the `toolbeam-docs-theme` plugin), built as a
Cloudflare adapter server app, mounted at `base: "/docs"` on the `opencode.ai`
domain. It is NOT the main marketing site — that's `packages/console/` per the
earlier task's correction, and this task confirms that correction is accurate.

In addition to the docs tree, `packages/web` also contains:
- A homepage/hero component (`src/components/Lander.astro`) used for the docs
  site's landing page (install instructions, feature list, screenshots) — this
  is a secondary/docs-adjacent landing page, not the full marketing site.
- A "share" feature (`src/pages/s/[id].astro`, `src/components/Share.tsx`,
  `src/components/share/*`) that renders shared opencode session transcripts
  (the `/s/:id` public link feature mentioned in the docs' "Share" section) —
  this imports types from the `packages/botconnector` workspace package.
- Full i18n: 18 locale JSON files (`src/content/i18n/*.json`, English + 17
  translations) and 17 translated docs trees (`src/content/docs/{locale}/`,
  ~578 files) mirroring the 36 English doc pages, in addition to the English
  ones (36 files) at the top level of `src/content/docs/`.

This is a **much larger surface** than the brief anticipated ("Starlight
title/config... probably sufficient"). Total raw "opencode" (case-insensitive)
hits across the package before this pass: **1542 in English docs alone**, 614
markdown/MDX content files total across all locales. See "Scope decisions"
below for how I bounded the work.

## Changes made, file by file

### 1. `packages/web/astro.config.mjs`
- Line 34: Starlight `title: "OpenCode"` → `title: "BotConnector"` (renders in
  the docs nav bar / browser tab title, since `logo.replacesTitle: true` means
  it's screen-reader-only text but still the accessible/SEO title).

### 2. `packages/web/src/content/i18n/*.json` (all 18 locale files)
Each locale file had the identical key set with brand mentions on lines
22–28 and 56–57 (image captions/alts, share meta description, and two
share-page labels). I did a case-sensitive whole-file replace of the literal
tokens `OpenCode`→`BotConnector` and `opencode`→`botconnector` on **values
only**, then had to fix a self-inflicted mistake: the same replace also hit
the JSON **keys** `share.opencode_version`/`share.opencode_name`, which are
looked up by literal string in `src/pages/s/[id].astro:51-52`
(`tx("share.opencode_version")`) and used as object property names in
`src/components/Share.tsx:308-309`. I reverted just the key names back to
`share.opencode_version` / `share.opencode_name` in all 18 files (values
stay renamed). Verified with a Node script: all 18 files parse as valid
JSON, have an identical key set to each other, and both `share.opencode_*`
keys are present in every file.

Example (`en.json`):
```
- "app.lander.images.tui.caption": "opencode TUI with the tokyonight theme",
+ "app.lander.images.tui.caption": "botconnector TUI with the tokyonight theme",
- "share.opencode_version": "opencode version",
+ "share.opencode_version": "botconnector version",
- "share.opencode_name": "opencode",
+ "share.opencode_name": "botconnector",
```
(key name `share.opencode_version` unchanged, only its value.)

Two locales (`bs.json`, `zh-TW.json`) used title-case `OpenCode` in these
same value strings (rest of their sentences stay in the local language,
"OpenCode"/"opencode" was left as an untranslated proper noun) — those became
`BotConnector` (title case), matching their original casing convention.

### 3. `packages/web/src/content/docs/*.mdx` (36 English/root-locale files only)
Word-boundary, case-sensitive replace of `OpenCode` and `Opencode` (both
brand-mention casings found in the English content) → `BotConnector`, across
frontmatter `description:` fields and body prose in all 36 top-level docs
pages (index.mdx, cli.mdx, config.mdx, providers.mdx, zen.mdx, etc.).
417 lines changed across 34 of the 36 files (`custom-tools.mdx` and `sdk.mdx`
had zero `OpenCode`/`Opencode` title-case brand mentions to begin with, so
git recorded no diff for them).

Deliberately **left untouched** (verified by the exact-case grep before
editing, and spot-checked in `index.mdx`, `cli.mdx`):
- Lowercase `opencode` in runnable command examples (`` opencode ``,
  ``/connect``, install commands) and package/formula/image names
  (`opencode-ai` npm, `anomalyco/tap/opencode` Homebrew, `opencode-bin` AUR,
  `ghcr.io/anomalyco/opencode` Docker) — these name real, currently-live
  opencode infrastructure; the actual installable binary a reader gets from
  those real channels is still literally named `opencode`, so leaving these
  as-is keeps the instructions accurate rather than inventing a
  `botconnector-ai`/`botconnector` package that doesn't exist on those
  registries.
- ALL-CAPS `OPENCODE_*` environment variables (67 distinct names found:
  `OPENCODE_API_KEY`, `OPENCODE_CONFIG`, `OPENCODE_SERVER_PASSWORD`, etc.) —
  real env vars the actual (unrenamed, per scope boundary) `packages/botconnector`
  binary reads.
- camelCase SDK identifiers (`createOpencodeClient`, `createOpencode`) — real
  exports from the actual `@opencode-ai/sdk` npm package, unrenamed.

I verified my regex doesn't clip these by testing it against a synthetic
line containing all these patterns together before running it for real (see
"Verification" below).

### 4. Import-specifier fix (not branding — a build-correctness fix)
`packages/botconnector/package.json`'s `"name"` field was changed from
`"opencode"` to `"botconnector"` in an earlier commit (per
`.rebrand-cli-tui-report.md`), and `packages/web/package.json`'s workspace
devDependency was updated to match in commit `73df8a165d` ("fix: update
packages/web workspace dependency from opencode to botconnector" — already
present on this branch before I started). However three `import type`
statements inside `packages/web` still referenced the **old** package
specifier `"opencode/..."`, which no longer resolves (there's no
`node_modules/opencode` workspace link anymore, only
`node_modules/botconnector`):

- `src/components/Share.tsx:8-10` — `from "opencode/session/message-v2"`,
  `"opencode/session/message"`, `"opencode/session/index"`
- `src/pages/s/[id].astro:4` — `from "opencode/session/index"`
- `src/components/share/part.tsx:30` — `from "opencode/session/message-v2"`

All five changed to `"botconnector/session/..."`. These are `import type`
only, so this wasn't breaking the runtime bundle (type imports are erased),
but it would break `astro check`/`tsc` typechecking. I judged this in-scope
since it's a direct, mechanical consequence of a rename already committed
inside the packages/web/opencode boundary, not a new architectural decision.

## Scope decision: 16 translated docs subdirectories NOT touched

`src/content/docs/{ar,bs,da,de,es,fr,it,ja,ko,nb,pl,pt-br,ru,th,tr,zh-cn,zh-tw}/`
— roughly 578 additional `.mdx` files — were intentionally left untouched in
this pass. Reasoning:

- Scale: this is ~16x the English content, i.e. genuinely a separate,
  substantial undertaking, not "split further if you find a bit more" scope.
- Same mixed technical/prose problem as English, but I cannot verify in
  16 languages I don't read whether a given `opencode`/`OpenCode` token is a
  translated brand-name sentence (safe to rename) vs. an embedded real
  command/package name/env var (must NOT be renamed) vs. something
  language-specific I'd misjudge. The English pass was defensible because I
  could read every changed line; a blind regex across Arabic/Thai/Japanese/
  Korean content I can't read is a materially different risk profile even
  though the mechanical technique (word-boundary `OpenCode`/`Opencode`
  replace) would likely carry over correctly for most lines, based on the
  identical-pattern sample I checked in `i18n/*.json` (locale text keeps the
  brand name as an untranslated proper noun, same casing convention).
- **This is flagged, not silently dropped**: if the team wants full parity,
  the i18n JSON approach used here generalizes directly — the same
  word-boundary sed script, run per-locale-directory with a native-speaker
  or second-pass review, would very likely be safe and fast. I did not do it
  myself because it exceeds what I judged in-scope for this pass without
  explicit confirmation, per the brief's own framing of expected scope.

## Genuinely ambiguous case flagged (not resolved unilaterally): `V2Banner.astro`

`src/components/V2Banner.astro` is a site-wide banner (rendered via
`PageFrame.astro` on every docs page) reading:
```html
<a class="v2-banner" href="https://opencode.ai/v2">
  <span class="badge">New</span>
  <span class="text">OpenCode v2 is now available</span>
  ...
```
This isn't a generic "the product is called OpenCode" mention — it's a
factual announcement that a specific real version ("v2") shipped, linking to
a real page about that real release. Applying the literal
prose-rename-but-not-the-link rule here would produce
**"BotConnector v2 is now available"** linking to `opencode.ai/v2`, a page
that is not about BotConnector at all and doesn't corroborate the claim —
i.e. a banner that's actively false/misleading rather than merely
pointing at upstream infra (the intended, acceptable kind of staleness
elsewhere in this pass). I left both the text and the link untouched and did
not guess at a resolution (delete the banner? hide it? something else?) since
that's a product decision, not a text-substitution one. Flagging per the
brief's explicit instruction to escalate genuinely ambiguous domain/URL
cases rather than resolve them myself.
